# Метод исследования

## Текущая реализация экспериментального контура

Офлайн CLI запускает восемь конфигураций на одном корпусе и наборе запросов. Основные четыре:

1. `fixed_k`: FTS5/BM25, фиксированный top-5.
2. `adaptive_k_score_gap`: за один запрос выбирает число фрагментов по относительному перепаду BM25-score. Порог 0,55 задан заранее; это наша эвристика, а не реплика Adaptive-k, где используется плотное сходство.
3. `sufficiency_guided_no_judge`: увеличивает пул кандидатов по шагам и записывает решение семантического судьи как `unknown`, поскольку судья не подключён. Это контроллерная заготовка, а не полноценный sufficiency-guided baseline.
4. `proposed_evidencerag`: тот же бюджетный контроллер дополнительно сохраняет различие датированных редакций и буквальных расхождений внутри редакции; он не определяет истинность, отмену положения или смысловую достаточность.

`fixed10_sensitivity` — дополнительная фиксированная точка. Три абляции выключают учёт редакций, буквальные сигналы конфликтов и итеративное расширение. Без учёта редакций literal-различие может отображаться как неуточнённый сигнал; это именно ablation устаревшего поведения, не продуктовая политика. Абляцию semantic sufficiency отключать нельзя: семантический судья ещё не реализован.

Для всех конфигураций общий верхний бюджет: 3 итерации, 20 уникальных фрагментов и 500 мс на запрос. Фиксированный top-k останавливается раньше; фактические фрагменты, символы и время сохраняются и сравниваются как затраты. Это одинаковые ограничения, не одинаковое фактическое потребление ресурсов.

## Данные и разметка

- `datasets/evaluation/cases.json` хранит `expected_resolution`: `supported`, `insufficient`, `versioned_difference` или `within_edition_conflict`.
- `required` содержит дословные обязательные отрывки только когда такой эталон определён. Три датированных примера теперь содержат правильный эталон и строку источника; прежние пустые эталоны не позволяют оценивать поиск по дате.
- `evaluation_cluster` отделяет семейство документов от фильтра retrieval. Все редакции одной семьи находятся только в одном split: train=device, dev=api, test=service/conflict/bundle.
- Набор авторский и синтетический. Он годится для тестов контроллера и регрессий; не является независимой эмпирической проверкой.
- Контроллер не читает `expected_resolution`, gold answer или `required`.

## Метрики и статистика

Измеряются precision/recall по размеченным чанкам, покрытие требуемых точных отрывков, F1 буквального конфликта в одной редакции, F1 различия между версиями, число итераций/фрагментов/символов и задержка.

Метрики answer correctness, semantic sufficiency, false abstention, unsupported answers, faithfulness и цена API — `null`: свободной генерации и judge нет. Раньше отсутствие демонстрационного `formal_rule` считалось отсутствием ответа; получалось `False Abstention=1.0`. Это число не характеризует качество контроллера и отменено. В прежнем прогоне также смешивались изменения версий и конфликты.

В test сейчас три независимых синтетических кластера. Этого недостаточно для доверительных интервалов и статистических выводов, поэтому run-004 не публикует p-value, bootstrap CI или тезис о превосходстве. Для статьи нужны больше независимых корпусов/семейств, двойная разметка и заранее зарегистрированные парные сравнения кластеров. Повторные вопросы одной семьи не считаются независимыми наблюдениями.

## Воспроизводимость

Каждый каталог run содержит commit, dirty-state, версии Python/SQLite, конфигурации, хеши исходников и входов, сырые предсказания, стабильные content-derived IDs источников, позиции в исходниках, рейтинги, трассы действий, метрики CSV/JSON и фактическую задержку. Каталоги не перезаписываются. Время измерения меняется между запусками; решения, выбранные фрагменты и агрегаты без latency должны совпадать.

Точная команда:

```sh
PYTHONPATH=apps/api .venv/bin/python -m packages.research.runner --output experiments/run-004 --split test
```

## План научной проверки

1. Получить лицензированный реальный корпус технических инструкций/регламентов с цепочками изменений и правилами применимости.
2. Независимо разметить тип отношения редакций, применимость, минимальные доказательства, достаточность и корректные причины отказа; adjudication расхождений.
3. До просмотра test зафиксировать Adaptive-k и сильный sufficiency-guided baseline, подключив их оригинальные модели/коды или чётко обозначив адаптацию.
4. Измерять качество retrieval отдельно от judge, генератора, фактической корректности и faithfulness. В генеративной части держать одну модель/шаблон и одинаковые токены/вызовы.
5. Сравнивать методы попарно на одних запросах; единица bootstrap — независимое семейство/корпус. При малом числе кластеров показывать описательные значения и широкие ограничения, не выводить значимость.

Исторические run-001—run-003 оставлены без изменений и описывают старый, методологически некорректный счётчик отказов. Актуален только run-004 с новой схемой, когда он успешно завершится.
