# Конвейер

Upload → проверка размера/расширения/даты → изолированный парсер → исходные фрагменты с locator/page/offset → нормализация → FTS5 → BM25 → ограниченный контроллер → сигналы полей/пробелов → политика результата.

Chunker режет блоки по 1100 символов без overlap. PDF сохраняет номер страницы, DOCX — заголовок и номер блока с таблицами, Markdown — последний заголовок, TXT — начало документа. Для точного визуального позиционирования в PDF нет координат символов: проверка выполняется по извлечённой странице и оригиналу.

Query: до 1000 символов, первые 32 уникальных нормализованных термина, пунктуация не попадает в FTS expression. Пользовательский текст не используется как SQL. `as_of` отсекает будущие и недатированные документы и выбирает последнюю дату в группе. Явная версия и дата применяются одновременно.

Контроллер: fixed5/fixed10 — один запрос; adaptive начинает с 4 и расширяет поиск недостающих терминов; versioned дополнительно просматривает совпадающие фрагменты в найденных группах. Максимум 3 итерации/20 выбранных фрагментов/500 мс по умолчанию. SQLite progress handler прерывает долгие поисковые операции; 50 мс busy timeout. Это кооперативный бюджет с небольшим overhead, не hard-real-time SLA. Семантических уточнений запроса нет.

Состояния: `no_results`, `insufficient`, `unverified`, `potential_conflict`, `confirmed_formal`; ошибки — HTTP с понятным русским сообщением. `confirmed_formal` доступен только авторским демоправилам с точным нормализованным вопросом, явно выбранной версией и обязательным текстом. Приватный upload не принимает правила от клиента.

Сигнал конфликта: одинаковая группа и ключ в строках `ключ: значение`, разные строковые значения. Допустимые изменения версии и реальные смысловые противоречия этим способом не различаются. UI явно называет результат сигналом и предлагает уточнить применимость. Свободное обобщение без оценщика поддержки запрещено.
