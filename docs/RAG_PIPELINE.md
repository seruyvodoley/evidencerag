# Конвейер

Upload → проверка размера/расширения/даты → изолированный парсер → исходные фрагменты с locator/page/offset → нормализация → FTS5 → BM25 → ограниченный retrieval controller → сигналы полей/пробелов → политика результата.

Chunker режет блоки по 1100 символов без overlap. PDF сохраняет номер страницы, DOCX — заголовок и номер блока с таблицами, Markdown — последний заголовок, TXT — начало документа. Для точного визуального позиционирования в PDF нет координат символов: проверка выполняется по извлечённой странице и оригиналу.

Query: до 1000 символов, первые 32 уникальных нормализованных термина, пунктуация не попадает в FTS expression. Пользовательский текст не используется как SQL. `as_of` отсекает будущие и недатированные документы и выбирает последнюю дату в группе; явная версия и дата применяются одновременно. `as_of` рассчитан на полные snapshots и не объединяет частичные поправки.

Контроллер:

- `fixed5`/`fixed10` — один поиск с постоянным top-k.
- `adaptive` — один поиск до верхнего лимита и выбор top-k по относительному порогу FTS5 BM25. Порог 0,55 — наша фиксированная эвристика; это не метод Adaptive-k из EMNLP.
- `sufficiency_guided` — интерфейс итеративного judge→gaps→retrieval. Без явно переданного judge оценка остаётся `unknown`; система расширяет кандидатный пул и не объявляет его семантически достаточным.
- `versioned`/`evidencerag` — ограниченное расширение контекста и просмотр совпадающих фактов в найденных группах редакций. Значения разных известных дат — `versioned_difference`; конфликт помечается только при разных literal значениях в одной и той же известной области редакции. Если область не установлена, используется `applicability_unknown`.

Каждый поиск имеет ограничение до 5 итераций/50 уникальных фрагментов/5000 мс; стандартный API использует до 3/20/500. SQLite progress handler прерывает долгие запросы; это кооперативный бюджет, не hard-real-time SLA. Трасса включает action, причину, судейское решение (включая `unknown`), новые и выбранные chunk IDs, gaps и время.

Стабильный `evidence_id` строится из неизменяемого содержимого и позиции фрагмента; `provenance` включает стабильный ID редакции, номер страницы/раздел, offset и ранжирующий score. Верификация истинности источника по этому ID не предполагается.

Состояния API: `no_results`, `insufficient`, `unverified`, `versioned_difference`, `potential_conflict`, `confirmed_formal`. `confirmed_formal` доступен только авторским демоправилам с точным нормализованным вопросом, явно выбранной версией и обязательным текстом. Приватный upload не принимает правила от клиента. Семантических уточнений query и свободной генерации нет.

Сигналы полей работают только на строках `ключ: значение`. Они не определяют entailment, истинность, редакционное намерение или правовой эффект поправки. UI показывает разные даты и не выбирает правильный ответ вместо пользователя.
